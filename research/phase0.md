# 階段 0 研究報告（2026-10-05）

遊戲：GTA V Enhanced（Steam 3240220），執行期基址 `0x7ff7d38b0000`，SizeOfImage `0x5b45200`。
傾印：`research/dump/GTA5_Enhanced.dump.exe`（不進版控；`.text` 熵值 7.99 → 6.59 表示已解密）。
工具：`tools/dump.py`、`tools/scan.py`、`tools/disasm.py`、`tools/screen.py`、`tools/keys.py`。

## 1. 原生函式（natives）— 可行

- `InitNativeTables(scrProgram*)` 位於 RVA `0x91bf20`
  （特徵碼 `EB 2A 0F 1F 40 00 48 8B 54 17 10`，命中點 -0x2A）。
  - 讀 `+0x2C` 原生數量、`+0x40` 原生陣列（輸入為雜湊、輸出為處理函式指標）。
  - 註冊表：256 桶（以雜湊低位元組索引），節點的 next 指標經 XOR 混淆。
  - 找不到的雜湊填入預設處理函式（`lea r10, ...`）。
- 作法：配置假的 `scrProgram`，填入雜湊陣列後呼叫原函式 → 取得全部處理函式。
- 雜湊：Enhanced 的執行期雜湊與公開（原始）雜湊**不同**，需要 crossmap（約 6,596 筆，其中 6,435 筆不同）。
  社群 crossmap 自 2025-03 以來未變更 → Enhanced 更新時並未輪換雜湊，維護成本低。
- 呼叫慣例：`scrNativeCallContext`（0x80 bytes：ret@0x00、argc@0x08、args@0x10、向量修正@0x18..）。

## 2. 腳本執行緒 — 可行

- `RunScriptThreads(int ops)`：特徵碼 `BE 40 5D C6 00`，命中點 -0xA（RVA `0x920a40`）。
- `ScriptThreads`（`atArray<scrThread*>`）：`48 8B 05 ? ? ? ? 48 89 34 F8 48 FF C7 48 39 FB 75 97`，+3 RIP。
- 在原函式之後，借用一個遊戲腳本執行緒（`main_persistent` / `startup`）的身分執行模組的 tick。

## 3. 資源模組（檔案系統）— 可行，且不需要金鑰

| 用途 | 特徵碼命中 RVA |
|---|---|
| 跳過 `rpf.cache` 檢查（把目標函式改成 `ret`） | `0x4f73ae` |
| fiDeviceLocal OpenBulk / GetAttributes（vtable 1） | `0x10b110` / `0x10bc10` |
| fiDeviceLocal OpenBulk（vtable 2，DirectStorage 路徑） | `0x107f60` |
| 加密類型判斷 / 標頭解密（允許 OPEN 未加密 RPF） | `0x10fef2` / `0x10ff08` |
| ParseHeader（未加密 RPF 條目修正） | `0x10f5b0` |
| 初始掛載（加掛自訂 device，例如 `dlcpacks:/`） | `0x4f8987` |
| OpenArchive（資料夾當成封存檔開啟） | `0x10f210` |
| GetDevice | `0x10caf0` |

- NG 加密的 RPF 由遊戲本身解密；OPEN（未加密）RPF 只要繞過解密 → **完全不需要擷取金鑰**。
- **時機很關鍵**：檔案系統 Hook 必須在遊戲初始掛載**之前**安裝，比「等到解殼完成」還早。
  已知可行的做法：在 DllMain 裡 Hook `kernel32!GetSystemTimeAsFileTime`，
  第一次被呼叫時（已解殼、尚未掛載）再進行掃描與 Hook。Enhanced 的匯入表經過混淆，不能用 IAT Hook。

## 4. 線上安全閥

- 呼叫原生函式 `NETWORK_IS_SESSION_STARTED` / `NETWORK_IS_GAME_IN_PROGRESS` 判斷即可，不需要額外特徵碼。
- 另外檢查命令列是否帶 `-nobattleye`；沒有的話整個載入器停用。

## 6. 階段 2 補充驗證（2026-10-05）

- 原生函式註冊表 RVA `0x3ED4C20`：256 桶；節點 next@+0x00（XOR 節點位址混淆）、7 個 handler@+0x10、
  數量@+0x48、雜湊@+0x54+i*16（皆 XOR 混淆）。執行期共 6,748 個原生函式（`tools/natives_dump.py`）。
- 公開雜湊 → 執行期雜湊必須用 crossmap；`SYSTEM`（BUILTIN）類維持不變。
  以「處理函式位址順序」自行推導：各命名空間內順序一致率 96.6%，不足以作為正式資料（錯 3% 會呼叫錯函式）。
- 目前腳本執行緒：`TLS[_tls_index]+0x7A0`，執行中旗標 `+0x7A8`，另有全域副本（特徵碼 `ActiveThread`）。
- scrThread：id@+0x08、state@+0x18、名稱雜湊@+0x150（= joaat(名稱)）、名稱@+0x154。
- scrNativeCallContext：回傳指標@+0x00、參數數量@+0x08、參數陣列@+0x10（每個 8 bytes）。
- 很多原生函式處理常式被 Arxan 切碎（jmp 到第二個 .text），用 `tools/trace.py` 追蹤。
- 實測：hello_mod 在故事模式讀到玩家座標、F5 生成 Adder 並坐進駕駛座。

## 7. 主畫面「故事模式」入口（2026-10-05，硬體寫入監看 + 靜態分析）

- 主畫面（Gen9 landing page）是 C++ 原生 UI，原生函式（SHUTDOWN_AND_LOAD_MOST_RECENT_SAVE）對它無效。
- `landing_pre_startup` 腳本只做：`while (native1()) WAIT(0); while (!native5()) WAIT(0);` 然後啟動 `startup`。
- 主畫面的所有卡片都經過 **Gen9 Script Router**：待處理請求是字串
  `source=<SRCS_*>,mode=<SRCM_*>,argType=<SRCA_*>,arg=<...>`，存在 atString（RVA `0x472B5A8`）。
  - `SetRouterLink(const Link*)`（RVA `0x13C4F30`）：由 `{source@0, mode@8, argType@0x10, arg@0x18}` 組字串，已有請求時不覆蓋。
  - `ClearRouterLink()`（RVA `0x13C4F00`）。
  - 主畫面每幀在 `0x5368B0` 讀取請求：`mode==SRCM_LANDING_PAGE && argType==ENTRYPOINT_ID` → 開主畫面入口；
    其他 → `SetFlowState(0x18)`（RVA `0x10780`），保留請求讓後續轉場依 `mode` 決定去處。
  - 列舉：SRCS_LANDING_PAGE_SP=4；SRCM_FREE=1（線上）、SRCM_STORY=2；SRCA_NONE=1。
- ⚠️ 單獨呼叫 `SetFlowState(0x18)`（沒有請求）會走**線上**流程，被 BattlEye 擋下（已實測，勿用）。
- 載入器做法：在腳本執行緒呼叫 `SetRouterLink({4, 2, 1})`，回讀字串確認含 `mode=SRCM_STORY`，
  否則 `ClearRouterLink()` 並退回原本主畫面。實測 17 秒進入故事模式，43 個腳本、無 `MainTransition`。

## 9. 原生暫停選單注入（2026-10-05，實驗 experimentalPauseMenu）

- `LoadPauseMenuData(1)`（RVA `0x5C5C00`）只把 pausemenu.xml 排入解析；同一執行緒稍後由解析器（`0xAE5A47`）填入
  全域選單物件 `0x3DFCF20`（screens atArray @+0x10）。
- **選單的執行期快取在「第一次開啟暫停選單」時建立**，不是啟動時。資料只要在第一次開啟前改好，C++ 就會照著用。
- CMenuScreen 0x50：items atArray @+0x08、id @+0x40、depth @+0x44。CMenuItem 0x28：target @0、label @4、
  條件 atArray @0x10、pref @0x20、optionType @0x21、action @0x22。
- 文字：TheText（特徵碼 `48 8D 0D ? ? ? ? 89 FA E8 ? ? ? ? 84 C0 74 ? 48 8D 0D`）+0x270 覆寫雜湊表可新增標籤（已實作）。
- 設定分類可否選取依「目標畫面 ID」決定（110/112/132 不行；139 語音聊天可選但頁面在故事模式整頁停用）。
- 在一般清單頁（通知 93）附加項目：可顯示、可操作；**但自訂 pref 編號會對應到其他真實設定的儲存位置**
  （218 的滑桿改到了 index 24）。在弄清楚設定值的存放/索引方式之前，不可使用自訂 pref。

## 10. 原生「模組」分頁與模組設定（2026-10-05，build 0x6aa45f10）

- 先前「分類被跳過／右欄進不去」是測試工具按鍵按住 0.15 秒觸發選單連發造成的假象，遊戲沒有目標頁 ID 白名單。
- 每個 CMenuScreen +0x28 指向處理類別雜湊，選單第一次開啟時由工廠表（0x5C8510）建立 C++ 處理物件存到 +0x00。
- 欄位建構 `0x5D0690(screenId, flag)`：每次顯示欄位（包含游標停在分類上時的右欄預覽）都會呼叫，從 pref 陣列讀值。
  顯示用的 pref 陣列 `0x3DFC2A0`，已存檔值陣列 `0x3DFC610`；兩者不同時該項以斜體顯示。
- 選單事件處理 `0x5EF9E0(event*, args*)`：事件 `0x610E6168` = 選項變更（args[0] pref、args[1] 新值，GFx number 型別 `&0x8F == 3`）。
  只有在分頁堆疊最上層（`0x3DFCBF8` 指標、`0x3DFCC00` 數量，16 位元組一筆）是 6（設定）時才呼叫 `0x5C7040(pref, value, 1)` 寫入。
- 畫面陣列依 id 排序（二分搜尋），在第一次開啟前追加新 id（最大 id 之後）的畫面可正常運作。
- 實作：分頁 42 改為設定版面；每個有設定的模組一個分類 + 一個新頁面；15 個安全 pref 欄位在頁面間共用
  （hook 0x5D0690 換入該模組的值，hook 0x5EF9E0 把變更寫回模組並存 settings.json）。
- 選項列表：`CMenuArray+0x20`（`0x3DFCF40`）atArray，每筆 0x18：`{u32 id; u32* labels @+8; u16 count @+0x10}`。
  項目 optionType = 列表 id（0 = 滑桿）；建構時對每個標籤雜湊查 TheText（`0x51D620`），所以文字覆寫表可直接提供選項文字。
  遊戲自己的 id 都 < 100；我們在第一次開啟前追加 id 100..250 的列表給 ML_SETTING_LIST 使用。

## 11. DLC 包與未加密 RPF（2026-10-05，build 0x6aa45f10）

- RPF7 標頭 `{magic 'RPF7', 項目數, 名稱長度（bit 28-30 名稱位移）, 加密}`；遊戲檔案皆為 NG（`0x0FEFFFFF`）。
- 封裝開啟 `0x10FCB0`：先查 rpf.cache（`0x1100E0(裝置, 路徑)`），命中時 `[0]` = 明文目錄（標頭+項目+名稱），`+9` = 已解密 → 完全不解密。
- 解密分派 `0xAAADC0(加密, 金鑰索引, 資料, 大小)` 與上下文初始化 `0xAA9FE0`：只接受 NG/AES，其他值（含 'OPEN'）執行 int3。
  **這兩個函式受執行檔保護，hook 會被還原**（實測開頭位元組恢復原狀）。
- 項目格式（讀檔 `0x110D60` 確認）：檔案 `u64 = 名稱偏移 | 壓縮大小<<16（0=未壓縮） | (資料位置/512)<<40 | 資源旗標 bit63`，`+8` 原始大小，`+0xC` 加密旗標；目錄 `+4 = 0x7FFFFF00`、`+8` 第一個子項、`+0xC` 子項數。
- DLC 清單：`0xC29A50` 讀 dlclist.xml → 每條路徑 `0xC29FC0(管理器, 路徑)`（接 `%sdlc.rpf` 掛載）→ `0xC2A1C0(管理器)` 處理（也會掃 `platform:/dlcPacks/`）。進入故事模式時會再處理一次。
- 實作：hook `0xC2A1C0` 先登記 `ModLoader/mods/<包>/`；hook 快取查詢，對未加密的包回傳我們讀好的明文目錄（加密值改為合法的 AES，檔案本身未加密所以不會真的解密）。
  `IS_DLC_PRESENT(joaat(nameHash))` 實測為 1。
- setup2.xml / content.xml 格式：由遊戲讀取自己的 DLC 時擷取（SSetupData、CDataFileMgr__ContentsOfDataFileXml）。
- 內嵌封裝檔（例如 OpenIV 產生的附加車輛包裡的 `x64/vehicles.rpf`）的快取查詢路徑是 `<setup2.xml 的 deviceName>:/<包內路徑>`；
  載入器讀外層目錄時一併登記（`setup2.xml` 若有壓縮，用遊戲自帶的 zlib1.dll 解壓）。明文目錄的加密值填 NG（與遊戲自身封裝相同）。
- 封裝檔 vtable `+0x2488E90`：OpenBulk `+0x10`、ReadBulk `+0x38` 只做位移換算後交給上層裝置，不解密。
- **資源格式版本**：Enhanced 的 `vehicles.rpf` 內 yft = 171、ytd = 5（1105 個）；舊版（Legacy）附加車輛為 yft 162、ytd 13，
  遊戲會登記模型（IS_MODEL_IN_CDIMAGE = 1）但不會載入資源。舊版資源需要轉成 Enhanced 格式才能用。

## 12. 資源容器（轉換第 1 階段，2026-10-05）

- 資源大小編碼（遊戲 `0x1579E0`，舊版與 Enhanced 相同，已用 HSV 實際解壓大小驗證）：
  `base = 0x2000 << (f & 0xF)`；`count = (f & 0x10) + ((f>>2)&0x18) + ((f>>5)&0x3C) + ((f>>10)&0x7E) + ((f>>17)&0x7F)`；
  `size = count*base`，另外 `f & 0x8000000/0x4000000/0x2000000/0x1000000` 分別再加 `base/16`、`base/8`、`base/4`、`base/2`。
  版本 = `(sys>>28)<<4 | (gfx>>28)`；sys 旗標算虛擬區（結構），gfx 旗標算實體區（圖像/頂點）。
- 版本檢查在讀檔之前，依據目錄項目的旗標：舊版（yft 162、ytd 13）不會被讀取。
- Enhanced 原生封裝內的資源：**每一頁分開壓縮且加密**（串流解壓 `+0x22CA236`，每個 z_stream 只有一頁）。
- 我們的未加密封裝：版本旗標若為 Enhanced 版本，遊戲會讀取資料並**直接 inflate（跳過 16 位元組 RSC7 標頭，不解密）**，
  所以轉換後的輸出可用「RSC7 標頭 + 單一 deflate 串流」，不需要產生 Enhanced 的加密分頁格式。
- 資源壓縮用的是遊戲內建 zlib（`0x11F1E0`），不是 Oodle（Oodle 解碼器在此期間沒被呼叫）。
- 資源倉庫：TxdStore 物件 `0x3ED61C8`（建構時版本參數 5），`+0x40` 項目陣列（每筆 0x18：物件指標、參考數、名稱雜湊、父索引），
  `+0x48` 旗標陣列，容量 `+0x10`（80200）。adder 的貼圖字典可用 joaat 名稱找到，物件位於資源結構區頁首。
- Enhanced 貼圖字典（記憶體中）：`+0x20` 名稱雜湊 atArray、`+0x30` 貼圖指標 atArray；每張貼圖 `0x80` 位元組
  （vtable、`+0x28` 名稱指標、`+0x30` 指向結構區內另一個物件、`+0x48/+0x50` 執行期 GPU 物件）。

## 13. 貼圖字典轉換（轉換第 2 階段，2026-10-05）

- Enhanced 貼圖放置建構函式 `0x1192DC0`（vtable `+0x2708AF0`，由 `0x1C1F610` 呼叫）：
  `+0x08` 區塊數 × `+0x0C` 區塊位元組 = 像素資料大小；`+0x18/+0x1A` 寬高、`+0x1C` 深度、`+0x1E` 維度（1 = 2D）、
  `+0x1F` DXGI 格式、`+0x22` mip 數、`+0x28` 名稱、`+0x30` → `+0x58` 的 0x28 位元組視圖物件（遊戲填入）、`+0x38` 像素資料。
- 舊版貼圖（0x90）：`+0x28` 名稱、`+0x50/+0x52` 寬高、`+0x54` 深度、`+0x56` 每列位元組、`+0x58` D3D9 格式（FourCC 或列舉）、
  `+0x5D` mip 數、`+0x70` 像素資料。字典與頁面表格式兩版相同（`+0x08` 頁面表：8 個 0、結構區頁數、圖像區頁數、頁面指標）。
- 像素資料：各 mip 緊接存放（實測大、小尺寸繪製都正確）；每張貼圖 4KB 對齊。
- **資源每一頁會被配置到各自獨立的記憶體**：任何物件或貼圖資料都不能跨頁。轉換時圖像區用同一尺寸的頁，
  每頁至少放得下最大的貼圖，依大小 first-fit 裝箱；結構區只用一頁。
- 驗證：HSV 的 4 張貼圖轉換後，用 DRAW_SPRITE 在遊戲中以不同大小繪製，全部正確（tools/convert_ytd.py）。
- 已解決（約一半啟動時 DLC 資源沒登記）：串流影像登記 `0xCE40E0` 掃描封裝檔時，用 vtable `+0x200` 組完整檔名，
  依賴名稱表後面的 u16 父目錄表（`[packfile+0x20]`）。正常解密路徑會配置並由 `0x110060` 填好；快取路徑則假設快取的
  目錄已附上這張表。我們的快取目錄原本沒有 → 讀到堆積殘值 → 登記名稱變成 `//mltex.ytd` 或亂碼。
  現在讀目錄時一併產生父目錄表，連續 4 次啟動都正確載入。
- 登記流程：`0xCE40E0` 先看 rpf.cache 內的登記快取（`0x10F960` 依序讀出封裝狀態，我們的包不在其中）→ 退回掃描，
  每個檔案呼叫 `0xCE3320(登記表, 輸出, 檔名, 索引, 影像…)`。

## 14. 取得 Enhanced 原生資源的檔案格式（轉換第 3 階段準備，2026-10-05）

- 頁面表項目 = 頁面位址 | log2(大小 / 0x2000)。圖像區頁面位址的低位元另有標記（GPU 記憶體）。
  零頭頁（例如 base/2）不一定出現在頁面表中（adder.yft：旗標算出 21 頁，表中 20 頁）。
- FragmentStore `0x3ED6308`（版本參數 171），項目格式同 TxdStore。
- 原生資源用遊戲內建 zlib 解壓（Oodle 函式在此期間不會被呼叫）。**一個 zlib 串流會依序填入多個不相連的頁面**，
  過程中切換輸出指標，所以只看串流結束時的位置只會得到最後一頁。
- 方法：記錄每次 inflate 呼叫的輸出（位址、位元組，research/capture_hook.cpp），載入後依頁面表位址拼回
  （tools/rebuild_resource.py）。deluxo.yft 26 頁全部取得，指標為檔案格式；**三次啟動重組結果 MD5 相同**。
  tools/dump_resource.py 則是直接從記憶體還原（含放置後的改動，僅供對照）。

## 15. 模型結構比對（轉換第 3 階段，2026-10-05；舊版 01hsv.yft vs Enhanced deluxo.yft 檔案格式）

- **相同**的版面：fragType 根物件（`+0x08` 頁面表、`+0x30` 可繪物件、`+0x58` 名稱、`+0xF0` 物理 LOD 群組…）、
  可繪物件（`+0x10` 著色器群組、`+0x18` 骨架、包圍體、`+0x50..0x68` LOD、`+0x70` LOD 距離、`+0x90` 關節、`+0x130` 名稱）、
  著色器群組、模型、幾何體標頭（`+0x18..+0x30` 4 個頂點緩衝區、`+0x38..+0x50` 4 個索引緩衝區、`+0x68`…）。
  檔案中的 vtable 欄位是編譯時位址（基底 0x140000000），執行期會被覆蓋，內容不重要。
- **不同**：頂點／索引緩衝區與頂點宣告。
  - Enhanced 緩衝區與貼圖共用基底（放置 `0x11924A0` / `0x1192680`）：`+0x08` u32 元素數、`+0x0C` u16 元素大小（低 12 位）、
    `+0x10` 資源旗標（頂點 `0x00580409`、索引 `0x0058020A`、貼圖 `0x01A70208`）、`+0x18` 資料、`+0x30` GPU 視圖物件（遊戲填入）。
    頂點緩衝區（vtable `+0x2708B30`，放置 `0x1C1F740`）另有 `+0x38` 頂點宣告；結構共 0x40。
  - 舊版頂點緩衝區：`+0x08` u16 步長、`+0x10` 資料、`+0x18` 頂點數、`+0x30` 宣告；
    舊版宣告：u32 元件遮罩、u16 步長、u8、u8 元件數、u64 類型表（每 4 位元一個類型）。
  - Enhanced 宣告：每個語意槽的位移表（數十個 u32）＋ DXGI 格式、步長、遮罩等；由幾何體放置 `0x1ED6270` 經 `0x1ED5840`
    解析後建立 DX12 輸入版面（存在幾何體 `+0x08`）。待解。
- **Enhanced 頂點宣告**（解析 `0x1ED5840`）：槽 k 的格式（DXGI 值，1 位元組）在 `+0x104 + k`，位移（u32）在 `+4k`；
  `+0x138` 位元 0 = 每個元件獨立串流。槽：0 位置、4 法線、8/9 與 12/13 切線／副法線（語意 3、2）、16/17 骨骼權重、
  20/21 骨骼索引（R8G8B8A8_UINT）、24/25 頂點顏色、28–35 UV0–7。位移為依槽順序的累加。
  驗證：deluxo 位置 float3@0、法線@0x0C、權重 `00 00 FF 00`@0x18、索引@0x1C、顏色@0x20、UV0@0x24、UV1@0x2C，步長 0x34。
- 舊版宣告：u32 元件遮罩（位元 0 位置、1 權重、2 索引、3 法線、4/5 顏色、6–13 UV0–7、14 切線、15 副法線）、
  u16 步長、u8 元件數、u64 類型（每元件 4 位元：5 float2、6 float3、7 float4、9 4 位元組 UNORM…）。
  資料依位元順序排列。HSV 與 deluxo 元件組合相同，只是順序不同 → 頂點轉換 = 依槽順序重排元件。
- **著色器（grmShader）結構不同**：
  - 舊版（0x30）：`+0x00` 參數陣列（每項 16 位元組：u8 類型（0 = 貼圖、1 = 向量…）、`+8` 資料指標）、`+0x08` 著色器名稱雜湊、
    `+0x10` u8 參數數量等、`+0x18` 預設檔（sps）雜湊。參數名稱雜湊的位置待確認（緊接參數陣列的不是雜湊）。
  - Enhanced：`+0x00` 兩個 u32 雜湊、`+0x08` 參數資料指標陣列、`+0x10` 貼圖參考表、`+0x20` 參數描述表
    （8 位元組標頭，例：`02 07 00 08 23 00 00 0C`，接著是 (名稱雜湊, 資訊) 配對：貼圖槽 4/8/…；常數變數為打包值，例 `0x400003`）、
    `+0x38` 繪製分組等。每個實例都帶有所屬著色器程式（DX12）的參數版面。
  - 轉換方向：依著色器名稱從遊戲原生資源（例如原版車輛）取得 Enhanced 版面，再依參數名稱對應舊版的值。
- **Enhanced 著色器放置**（著色器群組 vtable `+0x271B490`，放置 `0x1ED4690` → 每個著色器 `0x1C117A0` → `0x1EDC010`）：
  - `+0x00` u32 效果（.fxc）名稱雜湊 → 載入時換成效果物件指標（`0x1F12140`）；
  - `+0x04` u32 魔術值 `0x6D657461`（"meta"）表示 `+0x20` 有參數中繼資料表；
  - `+0x34` u32 參數版面雜湊，與效果 `+0x50` 比對；`+0x3A` u16 舊位置的同一值（遊戲會搬到 `+0x34`）。
  - **版面不一致時**：沒有 meta → `int3`（除非除錯旗標，`0x1F12570` 只是字串比對）；有 meta → 依中繼資料表
    逐筆以名稱重新對應（`0x1EDC22A` 起）。轉換器可以寫入 meta 表，讓遊戲自己把參數對應到 Enhanced 的版面。
  - `+0x08` 常數緩衝區資料指標陣列（效果常數緩衝區數 × 8）、`+0x10` 貼圖指標陣列（遊戲複製成 8 份）、`+0x18` 另一個指標。
  - 中繼資料表：標頭位元組 0 = 常數緩衝區數、1 = 貼圖數、4 = 變數數；項目 (u32 名稱雜湊, u32 資訊)，
    資訊低 2 位元 = 類型、(>>2)&0x3F = 索引，與效果參數描述（效果 `+0x38`，每筆 12 位元組：u16 索引、u8 類型、`+8` 雜湊）比對。

## 16. 模型轉換第一版可運作（轉換第 3 階段，2026-10-06）

- **效果（.fxc）參數描述**：效果表 `+0x4F05C18`（串列頭；節點 `+0x10` 名稱雜湊、`+0x18` 效果）。效果資料 `+0x38`
  描述陣列（12 位元組：u16 索引、u8 類型 0 貼圖／1 緩衝／2 取樣器／3 常數、u8 暫存器、u32 **舊名**雜湊、u32 **名稱**雜湊），
  `+0x50` 每實例參數區塊大小、`+0x58..+0x5C` 各類數量與總數。舊版常數用「舊名」，重新對應比對的是「名稱」。
  舊版貼圖參數以取樣器命名，與強化版貼圖沒有名稱關聯；R* 的轉換保留了順序（新貼圖接在後面），所以依效果的貼圖順序對應。
- **實例 `+0x3A`（載入時搬到 `+0x34`）是參數區塊大小**，不是雜湊：遊戲重新對應後，若檔案中 `+0x08` 指向的空間
  ≥ 效果的區塊大小，就把結果複製回該空間。R* 的檔案一律預留較大的區塊，而且一律帶 meta 表。
- 實例 `+0x39` = 舊版 `+0x11`（繪製分組），`+0x3C..+0x3F` = 舊版 `+0x20..+0x23`。
- **頂點宣告完整格式**（0x140）：u32 位移[52]（不存在的槽 = 下一個存在槽的位移）、u8 每槽步長[36] @`+0xD0`、
  u8 DXGI 格式[36] @`+0x104`、`+0x138` = 步長 << 2（位元 0 = 每元件獨立串流）。
- 緩衝區視圖（0x20，`+0x30`）：vtable、0、u16 0x14、6 × 0xFF。貼圖參考（0x50）：旗標 `0x00260000`、`+0x1C` 1,1、`+0x20` FF 00 01 00 00 00 01 00、`+0x28` 名稱。
- **`ERR_GFX_STATE` 的原因**：`script_rt_*` 貼圖會被遊戲建立成渲染目標（儀表板）。原生檔案的旗標是 `0x01A60228`、
  用途 `0x21A`、`+0x42` = 0x40；一般貼圖旗標建立 RTV 會觸發 `DXGI_ERROR_INVALID_CALL` 並移除裝置。
- 診斷：`ModLoader\debug_dred.txt`（內容含 `layer` 時開偵錯層，需要 Windows「圖形工具」；遊戲使用系統的 D3D12Core，
  不是自帶的 611 版）＋ `tools/dbwin.py` 接收偵錯層輸出。
- 結果：HSV（舊版 01hsv）在強化版中正常顯示，連續 3 次啟動皆無錯誤。

## 17. 載入器內轉換（第 4 階段，2026-10-06）

- **NG 解密**：分派函式 `0xAAADC0(加密值, 金鑰索引, 資料, 大小)`，金鑰索引 = `(joaat(檔名) + 大小) % 101`
  （目錄用封裝檔名與檔案大小；一般檔用原始大小；資源用儲存大小）。舊版封裝檔用同一組金鑰，強化版的函式可直接解開。
  受保護的程式碼只能呼叫、不能 hook。
- **R* 封裝檔內的資源**：開頭 16 位元組不是 `RSC7`（旗標記在目錄項），後面是**未加密**的 raw deflate。
  OpenIV 製作的包則保留 `RSC7` 標頭。
- **卡死看門狗**（`0x12C4C0`）：每秒檢查主執行緒心跳，約 60 次未更新就寫入位址 0 讓遊戲當掉；
  它有一個暫停計數器（特徵碼 `8B 05 ? ? ? ? 85 C0 75 E2 48 8B 05 ? ? ? ? 48 39 C6`），不為零時不倒數。
  轉換期間把計數器加一。
- **渲染目標**不能用區塊壓縮格式（`0x1E8368A` 的 int3）：`script_rt_*` 若是 DXT，就把第 0 層解成 B8G8R8A8、mip 1。
- **content.xml**：舊版範本常列出包內沒有的檔案（例如 `carcols.meta`），舊版遊戲會略過，強化版則永遠無法進入故事模式。
  轉換時移除這些項目（資料檔與 change set 兩處），並記成警告。
- **模型重新分頁**：舊版虛擬頁、實體頁、新增頁都當成區塊，重新裝進遊戲的分頁大小等級（根物件固定在位移 0），
  再掃描整個區塊改寫指標（`0x5…`／`0x6…`）。強化版 yft 沒有實體區塊。內嵌貼圖字典原地轉換，像素搬到 4KB 對齊的新空間。
- 驗證：舊版 `mpluxe2`、`mpjanuary2016`、`mphalloween` 共 1778 個檔案轉換無錯誤；HSV、bugcent、mclsab 在遊戲中生成並正常顯示（兩次啟動）。

## 24. 啟動時隨機崩潰（2026-10-06）

- 現象：不裝模組也會發生，約每 6 次啟動 1 次，在讀取畫面時當掉，60 秒後由遊戲自己的「卡住偵測」主動讓遊戲崩潰

- 診斷：`debug/hangdump` 監看同一個心跳，停止 45 秒時寫出含所有執行緒堆疊的 minidump（`ModLoader\hangdumps`）。
  9 份中有 8 份是同一個死結：
  - 主執行緒：`… → 0x532240 → 0xc12f70 → 0x611a00`，在等繪圖器的讀寫鎖（全域 `0x3e07868`，等待函式 `0x13a600`）。

    在等 GPU fence。
  - `0x1e7bfe0` 是 `WaitFence(wrapper, value)`：`+0x10` 為 `ID3D12Fence`、`+0x18` 為快取的完成值，數值上半有旗標

    該 fence 值要等主執行緒送出的工作才會完成，因此兩邊互等。
- 修正（`game/fixes`）：只在讀取畫面執行緒內攔截 `WaitFence`；照原樣等待，但若已等 5 秒且主執行緒心跳也停了 5 秒，
  就放棄這次等待並記錄警告，讓讀取畫面放開鎖。讀取畫面只是畫一張圖，略過一次等待最多少畫一格。
- 另一個崩潰來源是系統記憶體：Steam 連續執行一個月後，steamwebhelper 佔用約 41 GB，認可記憶體逼近上限，
  在 `socialclub.dll` 內配置失敗而崩潰。重啟 Steam 後由 137.5 GB 降到 91.3 GB（上限 149.7 GB）。
- 驗證（重啟 Steam 後、裝了修正）：連續啟動 12 次全部正常（`tools/stress.py`，不送輸入，存活 130 秒算正常）。
  但這 12 次修正都沒有觸發，也沒有產生卡住 dump，表示這段期間死結根本沒發生；原本約 1/6 的機率下連續 12 次都正常約有 11% 機率，
  所以還不能證明修正有效。推測死結和記憶體吃緊有關（GPU 工作被分頁拖慢）。修正與診斷保留，之後若再發生，日誌會出現
  `fix:` 或 `hang:` 紀錄。

## 25. 替換型模組（2026-10-06）

- 放法：`ModLoader\mods\<名稱>\` 裡沒有 `dlc.rpf`、但有遊戲檔案（散裝檔案或 `.rpf`）的資料夾。同名的 `<名稱>.dll`
  存在時，那是程式模組自己的資料夾，不算。載入器把它打包成 `ModLoader\cache\<名稱>\dlc.rpf`，再走既有的 DLC 包流程。
- **串流檔案覆蓋**：DLC 的 `RPF_FILE` 預設不會蓋過原版同名檔案；`content.xml` 中加上 `<overlay value="true" />` 就會
  （以 Infernus 的檔案改名成 adder.* 實測，兩次啟動）。封裝檔名稱與路徑不必和原版相同，所以全部放進 `x64/ml_stream.rpf`。

- **資料檔**：DLC 的 `HANDLING_FILE`、`VEHICLE_METADATA_FILE` 中與原版同名的項目會被忽略（`overlay` 也無效），
  所以逐項覆蓋由載入器處理：
  - 資料檔由 `Register(path, size*, flags)`（`0x1275a40`）依名稱登記成串流代號；它先用搜尋路徑解析
    （`0x1021d0`，參數為搜尋路徑物件與空字串），再取得裝置。Hook 這裡：先用遊戲的 `fiStream`

    `CHandlingDataMgr/HandlingData|handlingName=adder`（不分大小寫）。已有鍵的項目裡面的 `<Item>` 屬於該項目
    （例如 `SubHandlingData`），不另外比對；同一檔案內重複的鍵不覆蓋。

## 26. 音效資料 `.rel` 與遊戲腳本 `.ysc`（2026-10-07）

### `.rel`（audio game data：game.dat151、sounds.dat54、speech2.dat4…）
- 格式：u32 類型、u32 資料大小、資料（u32 版本戳記 + 項目）、u32 名稱表大小、名稱表（u32 數量、u32 位移、字串）、
  u32 項目數、{u32 雜湊, u32 位移, u32 大小}、之後是數個「u32 數量 + 資料位移」的表（載入時要修正的欄位）。
  索引依 `rotr(值, 8)` 遞增排列（低位元組是分組）。戳記兩版不同（`0x6cbc0b` / `0x29b86d9`）。
- 項目第 1–3 位元組兩版不同，其餘部分 86–100% 相同（dat151 類型 52 只差 +4 的旗標）；dat54 名稱表在中間有插入，
  但項目不受影響，所以項目欄位不是名稱表索引。
- 遊戲讀的是 `update.rpf` 裡的版本（經 `fiStream::Open` 開 `audio:/config/*.rel`）。兩版 update 的 game.dat151 只差 7 項。
- 合併（`convert/rel.cpp`）：模組通常附整個舊版檔案。模組項目若與遊戲的相同（忽略 1–3 位元組），或等於舊版遊戲
  （原版或 update）自己的版本（`tools/learn_rel.py` 產生 `rel_tables.inc`：兩版不同的項目的舊版 CRC），就不套用；
  其餘附加到資料區尾端、索引指向新位置（保留遊戲的 1–3 位元組），模組表中落在該項目內的位移也一併加入，名稱表補上缺少的名稱。
  多個模組的 `.rel` 一起合併（名稱排前面的優先）。
- 實測：未修改的舊版 game.dat151 → 替換 0 項；只改一項的 sounds.dat54 → 替換 1 項；遊戲正常。

### `.ysc`（遊戲腳本）
- 兩版腳本都在 `update\update2.rpf` 的 `script_rel.rpf`（1154 支同名），資源版本都是 12，指令集相同（反組譯沒有未知指令），
  字串、靜態變數相同。
- 原生函式雜湊兩版**相同**：表中的值是雜湊右旋 `(程式碼大小 + 索引) & 63` 位（解碼要左旋）；程式碼大小不同所以存的值不同。
- 不同的是全域變數編號：程式標頭 `+0x18` 是全域變數配置簽章，舊版 `0x582CE9D8`、強化版 `0xA2BE51AC`（不用全域變數的腳本為 0）。
- 對照表：`tools/learn_ysc`（C++）把每對腳本先以函式（`ENTER`）為單位配對，內容不同的函式再用 Myers diff 對齊指令，
  配對 `GLOBAL_U16` / `GLOBAL_U24` 的運算元，每個舊版編號取最常配到的強化版編號 → `src/loader/convert/ysc_tables.inc`
  （5223 個，24 個有歧義）。全部腳本約 10 秒（Python 版約 15–20 分鐘）。

## 27. 程式分析與版本間重新定位工具 `tools/relocate`（2026-10-07）

- C++，x86 解碼用 Zydis（MIT，通用函式庫；不含任何 GTA 相關的外部分析成果）。離線工具，不在載入器內執行。
- 輸入：遊戲執行中的傾印（`tools/dump.py`）或一般 PE。函式來自 `.pdata`（強化版 72413 個），建索引約 1 秒（多執行緒）。
- 每個函式的指紋：去掉位址後的指令形狀（保留暫存器、結構欄位位移、小常數）雜湊、引用的字串、呼叫圖（被呼叫者依呼叫順序、
  呼叫者）、指令三連組的 MinHash（相似度）。
- 指令：`info`、`func`（邊界、呼叫者、被呼叫者、字串、反組譯）、`strings`、`xrefs`、`pattern`、`sig`（從位址起自動產生
  最短的唯一特徵碼，遮掉 RIP 相對位移、跳躍目標、位址立即值）、`match <舊> <新> <位址或清單>`、`stats`。
- 比對：唯一字串的使用者 → 雙方唯一的完全相同指紋 → 沿呼叫圖推進（已配對函式的被呼叫者 / 呼叫者，數量相同時依位置，
  否則取明顯最相似者）→ 查詢時仍未配對的，在已配對鄰居附近找最相似的。位址換算：函式內的位址以指令形狀序列對齊（LCS）
  找到對應指令；資料位址由引用它的已配對函式中對應指令的目標投票。
- 自我比對（同一傾印）：69746 / 72413 個函式配對（字串 2963、完全相同 59088、呼叫圖 7695），5 個已知目標
  （資料檔登記、開檔、讀取畫面、WaitFence、看門狗心跳全域）全部正確，總計約 2 秒。
- 跨版本實測：舊版 GTA5.exe（磁碟上加密，以 `-nobattleye` 啟動後傾印：`tools/dump.py <out> GTA5.exe`；30 秒後仍有
  3–17% 的程式碼頁在變動，所以少數函式可能仍是加密狀態）。舊版是 MSVC、強化版是另一個編譯器，指令序列差很多，
  「完全相同」只有 86 個，是比一般更新困難得多的情況。改進：
  - 與編譯器無關的特徵：函式用到的常數、結構欄位位移、`.rdata` 常數值（浮點數等）、呼叫數量（MinHash 估計相似度）。
  - 字串錨點只取 `.rdata`（`.data` 裡有執行時寫入的路徑等），並改為投票：一個函式的唯一字串多數指向同一個對象才配對。
  - 呼叫圖推進改為工作佇列；同長度清單同位置且指紋相同的直接配對，其餘取兩邊都明顯勝出的最佳分數；略過超過 200 個
    元素的清單（泛用函式）。
  - 位址換算：函式入口直接對應；指令形狀對不上時，以已配對的被呼叫者序列對齊呼叫指令。
- 準確度（`relocate eval`：一半的字串錨點留作答案）：同一版本 5382 對、0 錯、3 未找到；強化版 → 舊版 3235 對、93 錯、
  813 未找到（找到的正確率 97%）。舊版的 `fiStream::Open`（`0x1367484`）由強化版的 `0x102620` 正確找到並產生新特徵碼。
  實際的強化版小更新（同一編譯器）應接近同版本的結果。

### 45b. 平移被覆蓋的真正原因與修正（同日）

- 硬體寫入中斷點（loader.json `debugPoseWatch`，監看 SKEL_Spine_Root 的物件／局部矩陣）顯示每幀的寫入順序：
  主執行緒 post-animation 原函式 → 我們的覆寫 → 動畫工作執行緒做一次「骨架 → 動畫幀 → 骨架」的來回：
  - `0x22d5b90`：把局部矩陣讀成動畫幀（保留我們的旋轉與平移）；
  - `0x22d6c00`（工作：+0x20 局部矩陣、+0x18 預設值、+0x28 骨頭數）：先把局部矩陣整份換成預設值，再寫入幀裡的軌道，
    最後重算物件矩陣。幀只帶旋轉和少數骨頭（骨頭資料 +0x40 旗標含 0x70 的：ROOT、Spine1、前臂、手、臉…）的平移，
    所以骨盆、脊椎根、Spine0 的平移在這一輪消失，旋轉則保留。
  - 只改骨頭旗標無效（幀的軌道配置不隨之改變）。平移 SKEL_ROOT 會讓遊戲關閉（有 dump，14:36/14:39）。
- 修正（`src/loader/game/pose.cpp`）：
  - hook `0x22d6c00`（特徵碼在函式內 +0x6d，執行檔中唯一），在它之後以局部矩陣指標找到覆寫並重新套用；
    覆寫表改由互斥鎖保護（主執行緒與動畫工作執行緒）。
  - 副作用：動畫沒有軌道的骨頭，每幀會從上一幀的最終姿勢開始，也就是帶著我們的覆寫，相對量（下沉、前傾）會逐幀累積。
    因此在 post-animation 時擷取「腳本看到的動畫姿勢」：被覆寫的骨頭若仍等於我們上一幀寫入的值（容差 1e-3）就視為沿用，
    改用覆寫前保存的動畫值；動畫有寫入時則更新保存值。GetBone（非 SHOWN）回傳這份姿勢。
  - 覆寫結束或過期時，把沿用中的骨頭還原成保存值，只重算它們與子骨頭的物件矩陣。最初全部重算時，遊戲在結束時會關閉
    （輔助骨 MH_/IK_ 不是單純的正向運動學）。
- 驗證：下蹲 14 cm、前傾 18°。全身鏡頭中膝蓋彎曲、骨盆下沉、雙腳著地；慢動作特寫中持球時手掌在球上（紅點在手上）。
  連續 3 次執行，持球時手掌距離平均 0.8／−0.2／0.0 mm（最大 5 mm）、手腕誤差平均 3 mm 以下，沒有構不到的幀；
  覆寫結束後遊戲正常。

### 52.1 車底吸附風扇（2026-10-19）

- 做法：每格從車身中心沿車身「下」方向打探測線。下方 2 公尺內有面時，依車底離該面的距離施加吸力（沿面的法線方向，加在速度上）：
  - 離靜止高度 0.25 公尺內全額，0.8 公尺以外歸零；
  - 預設 2G（車重的倍數），可選 1–3G；
  - 靜止高度在平地上自動學習（約 0.48 公尺）。
- 只加吸力，不做任何「轉上牆」的輔助：直角牆會像一般車一樣撞上，坡度漸增的弧面才能一路開到垂直（使用者要求）。
  - 一開始做過偵測前方牆面、自動把車身轉上去的版本，已依使用者意見移除。
- 實測（機場柏油路，Roadster Performance）：
  - 側向抓地力：從 15 m/s 橫向滑到停，風扇開 3.0–3.3G，風扇關 1.7–1.9G。
  - 四分之一管道 `stt_prop_stunt_bblock_qp3`：車子從平地一路開到完全垂直，四輪貼面，車底維持 0.47–0.55 公尺，在垂直面上加速到 45 m/s，到道具頂端（約 57 公尺）飛出。
  - 開到 51.5 公尺放開油門：停住後貼著牆面倒退滑下。風扇關時只到 46.5 公尺，頂端車輪短暫離面。
  - 迴環 `stt_prop_ramp_adj_loop`：地面有兩條直線軌道，在圓環下方交叉成 X 形，入口要沿其中一條直線進入（從道具長軸進入會鑽過圓環或從旁邊經過）。
  - 約 19 m/s 時開上入口段，爬到 24 公尺；之後軌道向側邊扭轉，放開方向盤的自動測試開出軌道邊緣而翻落。倒立段尚未驗證。
- 測試用的道具：Cunning Stunts 的特技道具在故事模式也能生成（wallride、ramp_adj_loop、spiral、bblock_qp、tube 等，research 用 IS_MODEL_IN_CDIMAGE 確認）。

### 53.6 AI 第 1–2 步：接管框架與嫌犯徒步逃跑（2026-10-20）

- 使用者的目標：控制遊戲 AI，避免出現不符合情況、不像現實的選擇，並給嫌犯更合理的逃離方式。範圍包括報案嫌犯、遊戲警察、一般 NPC。
- 接管框架（`ai.cpp`）：
  - 由模組決定，遊戲只負責執行（走路、開車、射擊）。
  - `SET_BLOCKING_OF_NON_TEMPORARY_EVENTS` 擋掉遊戲自己對事件的反應；同時關掉自行逃跑，打開爬越、梯子、跳下。
  - 感知（每 200 毫秒）：
    - 距離。
    - 「看得到」：從頭部骨架對頭部骨架打射線，只算地圖和物件，不算人和車。它有兩種：互相可見（`visible`，背對也知道警察在哪，例如逃跑時回頭看、聽到腳步），以及在前方 200° 內（`seesPlayer`，用來第一次察覺）。
    - 警察有沒有拔槍、有沒有瞄準自己。
    - 支援人數、警燈第 2 段以上的警車在附近。
    - 自己有沒有受傷。
  - 壓力：被瞄準、拔槍、距離、支援、警燈、受傷加總。
- 嫌犯（`suspect.cpp`）：
  - 個人數值：膽量、敵意、罪責（例如身上的管制藥物級別、通緝）、持械（0–3）、清醒／酒醉／受管制藥物影響、能力等級（新手、普通、老手）。
  - 決策（每秒）：配合、拖延、逃跑、反抗、開槍，各自算分取最高。
    - 加上清醒程度和經驗的隨機雜訊。
    - 加上維持現狀的加分，以及最短維持時間（投降 5 秒、拖延 2 秒）。投降過一次的人，之後比較少再逃。
  - 逃跑或動手前會先有預兆：看向逃跑方向、轉身面對警察。老手 0.8 秒、普通 1.2 秒、新手 1.6 秒。
  - 選逃跑路線：
    - 在附近的導航網格上取點（新手 6 個方向、普通 12 個、老手 20 個，各取 22／40／65 公尺）。
    - 依四點評分：能不能拉開距離、路線會不會經過警察、到那裡警察還看不看得到、有沒有沿著原本奔跑的方向。
    - 越沒經驗，評分的隨機雜訊越大。新手每 4 秒重新規劃一次，其他人 3.5 秒。
  - 體力：全速衝刺會消耗（老手約 40 秒、普通 30 秒、新手 22 秒；酒醉或受管制藥物影響只有六成），慢下來會恢復。體力耗盡就只能用跑的，也更容易放棄。
  - 被追上：警察在 1.8 公尺內超過 1.2 秒，就比較傾向投降。
  - 躲藏：擺脫警察視線一段時間，且距離 20 公尺以上（新手要擺脫更久），就找附近警察「最後看到他的位置」看不到的點，蹲著躲。
    - 被發現就再跑或投降：看得到且 18 公尺內，或不論看不看得到只要 5 公尺內。
    - 躲到一定時間（新手 20 秒、普通 40 秒、老手 60 秒）沒被找到，就若無其事地走開；200 公尺外看不到時算逃脫。
  - 地圖：看得到時嫌犯有紅點；看不到時顯示最後位置附近 60 公尺的範圍。
- F4 →「Police」→「開發測試（嫌犯 AI）」可以在前方生成新手、普通、老手嫌犯來測試。
- 實測（羅伊洛文斯坦大道一帶，用腳本讓玩家追趕）：
  - 高罪責老手：
    - 察覺後逃跑，穿過兩棟房子之間的巷子，在警察看不到後躲進圍欄後面的花園。60 秒後走開，警察靠近時又跑。

### 53.7 AI 第 3 步：嫌犯開車逃跑（2026-10-20）

  - 隨機的普通嫌犯：一次靠邊停好，其他幾次（剛好都高罪責）逃跑；有兩次撞車卡住後下車跑。

### 53.8 AI 第 4 步：換車、換裝（2026-10-20）

- 換車：徒步逃跑時，如果和警察拉開 15 公尺以上，每 1.5 秒找一次附近能開的車。
  - 用 `GET_PED_NEARBY_VEHICLES` 找。條件：18 公尺內、能開、不是警車／船／飛機／直升機／火車／腳踏車，而且離自己比離警察近 8 公尺以上。
  - 會不會搶車看膽量：老手機率等於膽量，普通是膽量的六成；新手和酒醉的人不會。
  - `TASK_ENTER_VEHICLE` 旗標 8（有人在車上就拉出來），坐上駕駛座後改開車逃跑（§53.7）。10 秒內沒坐上，或警察追到 6 公尺內，就放棄繼續跑。
- 換裝：躲藏 6 秒後，普通（40%）和老手（80%）會換外觀：上身（環境 NPC 的 3 號、freemode 的 11 號）換成別的款式或顏色，帽子眼鏡拿掉。
- 換裝或換車後算「認不出」：警察要在 10 公尺內才認得出來，地圖紅點也只在那時顯示。被找到的距離從 18 公尺縮到 6 公尺；走開時要警察到 5 公尺內才會有反應。
- 實測（草莓大道，高罪責老手，三次）：兩次躲起來後換裝；一次逃跑中搶了路邊的車開走。換裝只看了記錄，沒有在畫面上確認衣服變了。

### 53.9 AI 第 5 步：支援警力的追捕行為（2026-10-20）

- 支援警員也由模組決策（`ai::TakeControl`，關係群組 COP）。有嫌犯被追捕時（`suspect::Pursued`），每個支援單位依嫌犯在做什麼分到一個角色，每 2.5 秒更新一次任務：
  - 嫌犯開車逃：距離最近的單位「跟車」。用 `TASK_VEHICLE_MISSION_PED_TARGET` 任務 7（跟隨），保持 15 公尺，不撞車，開警燈和警笛。
  - 第二個單位「設路障」：開到嫌犯路線目標附近的道路節點，停車、開警燈、下車。
    - 角色不會來回換：除非另一台明顯（50 公尺）更近才交換。
  - 嫌犯徒步：太遠先開車靠近（40 公尺），然後下車用跑的追，不開槍。
  - 嫌犯反抗或開槍：交火（`TASK_COMBAT_PED`）。只有這種時候才會開槍。
  - 嫌犯配合或在原地拖延：下車、拔槍走近到約 5 公尺，瞄著他（`TASK_GO_TO_ENTITY_WHILE_AIMING_AT_ENTITY`、`TASK_AIM_GUN_AT_ENTITY`），等玩家處理。
  - 沒人看到嫌犯（4 秒以上）：開到最後看到的位置，下車在 40 公尺內搜索。
  - 追捕結束：回到玩家身邊。
- 無線電：支援警員只要看得到嫌犯（開車時 150 公尺、徒步 60 公尺內，加上 `HAS_ENTITY_CLEAR_LOS_TO_ENTITY`），就更新全體共用的「最後已知位置」（`suspect::Spotted`）。
  - 換裝或換車的嫌犯要在 10 公尺內才認得出來。
  - 嫌犯判斷「甩掉、躲藏、被找到」時，也會算支援警員看不看得到，不只看玩家。
  - 嫌犯感受到的警察人數（壓力）改成 25 公尺內的支援警員數。
- 實測（羅伊洛文斯坦大道和草莓大道，兩組支援，玩家跟車）：
  - 開車逃跑：一台跟車、一台設路障，70 秒內角色穩定沒有亂換。
  - 嫌犯撞到公車後下車跑，兩台改成徒步追。嫌犯搶車後又改回跟車和設路障。
  - 配合的路人：支援從徒步追改成包圍瞄準。
  - 持槍兇嫌：逃跑、被追上後反抗，支援改成交火。
  - 以上只看了記錄，支援包圍瞄準和交火沒有在畫面上確認（鏡頭被圍欄擋住）。

### 53.10 AI 第 6 步：一般 NPC（2026-10-20）

- `ambient.cpp`，只在警察身分時運作。「一般 NPC」指：人類、不是玩家、不是任務實體（模組的嫌犯和支援都是任務實體），也不是警察、醫護、消防、特警。
- 讓路：玩家或支援的警車開著警燈（第 2 段以上）且時速超過 4 m/s 時，每 0.4 秒檢查一次車子附近的車（`GET_PED_NEARBY_VEHICLES`）。前方 4–45 公尺、左右 7 公尺內、同方向的一般車：打右方向燈，`TASK_VEHICLE_TEMP_ACTION` 27（靠右煞車）2 秒。不鳴笛也會讓。
- 圍觀和逃散（有嫌犯被追捕時，每 0.7 秒）：
  - 嫌犯配合或停著時：45 公尺內最多 4 個路人，每次 25% 機率，在 8–30 公尺處停下來，面向現場拍手機（`WORLD_HUMAN_MOBILE_FILM_SHOCKING`）或站著看。25–55 秒後離開。
  - 開槍時（嫌犯、支援或玩家，`IS_PED_SHOOTING`）：45 公尺內的路人立刻往遠離現場的方向找掩護逃跑（`TASK_SMART_FLEE_COORD`），圍觀的人也散開。
- 目擊者：嫌犯徒步或開車逃跑時，40 公尺內看得到他的路人（每 0.5 秒，最多 8 人）會記住看到的位置、方向（速度向量）、交通方式（車型名稱），記 5 分鐘。
  - 警察下車走到 20 公尺內時，目擊者頭上有黃色問號；2.5 公尺內按 E 詢問。
  - 目擊者會轉身面對警察回答，例如「剛剛有個人用跑的，往北邊去了。」「2 分鐘前有個人開一台○○，往東南邊去了。」看到的位置在地圖上標 40 公尺的黃色範圍，保留 60 秒。
- 實測（草莓大道）：
  - 老手嫌犯逃跑時，記錄到 2–5 名目擊者。走到其中一人面前按 E，得到「剛剛有個人用跑的，往北邊去了」，地圖出現範圍。
  - 追車 40 秒，讓路觸發 5 次（只看了記錄，畫面上的靠右效果沒有確認）。

### 53.11 AI 第 7 步：派遣、第一種報案（失竊車輛）、動作選單（2026-10-20）

- 派遣（`dispatch.cpp`）：上班中、沒有其他嫌犯時，每 2–5 分鐘由無線電來一件報案（提示音 + 通知）。
  - F9 →「派遣」→ 接受／忽略。45 秒沒回應就轉給其他單位。開發測試頁有「立即派遣一件報案」。
- 失竊車輛：
  - 在 500–900 公尺外的道路生成開車的嫌犯，罪責至少 0.7，能力隨機（老手 30%）。
  - 報案內容：「調度：扁柏平地有一台失竊的猛牛，車主剛報案。」區域名用 `GET_NAME_OF_ZONE` 的標籤翻成中文，車名用遊戲的中文名稱。
  - 接受後，地圖上出現嫌犯附近（偏移最多 30 公尺）150 公尺的黃色範圍，並設 GPS 路線。每 25 秒「民眾回報」一次新位置和行駛方向，直到警察（90 公尺內、看得到）找到那台車。
  - 結束：押上警車算逮捕，也可能嫌犯死亡或逃脫。結束後下一件報案在 2–5 分鐘後。
- 動作選單（使用者的設計：按住 E 對人或車）：上班中、徒步、在配合、拖延或已上銬的嫌犯 3 公尺內，按住 E 0.45 秒開啟，使用同一套遊戲內選單。
  - 在車上：叫他下車、盤查證件。
  - 徒步：盤查證件、搜身、上手銬（已上銬時改成押上警車）、放他走。
  - 盤查：英文姓名 + 紀錄（罪責 >0.8 有通緝、>0.6 有前科、其他無紀錄）。
  - 搜身：依持械找到刀、手槍、衝鋒槍，以及第 N 級管制藥物（只寫級別）；武器會被沒收。
  - 上手銬：`SET_ENABLE_HANDCUFFS`，加上 `mp_arresting idle` 動畫（上半身、循環；有人上銬時字典保持載入）。警察走開時嫌犯會跟上。
  - 押上警車：30 公尺內的警車（自己的巡邏車、最後開的車、支援的車，車輛類別 18），嫌犯走去坐後座；20 秒內沒坐上就直接放進去。
- 實測：
  - 配合的路人：被瞄準後舉手，按住 E 開選單，搜身 →「沒有搜到東西」，上手銬，押上警車，顯示「嫌犯已押上警車」。
  - 失竊車輛：
    - 報案、接受選單、黃色範圍和 GPS（874 公尺）都正常。
    - 用腳本開車追過去並開警燈：嫌犯從拖延轉成開車逃跑，最後「開車逃脫」，派遣顯示「嫌犯逃脫」。

### 53.12 查車牌、盤查、搜身搜車、支援協助、向調度查詢、報告（2026-10-20）

- 使用者的設計：
  - 車上電腦，但為了方便，直接從附近車輛的清單（含照片）選，不必手動打字。
  - 車牌用「對準前車自動讀取」加手動輸入。
  - 搜查分區、有時間和動畫。
  - 報告自動產生草稿，修改後提交。
- 資料（`records.cpp`）：
  - 人和車第一次被警察看到時才建立紀錄。
    - 人：英文姓名、生日、駕照（有效 85%、過期、吊銷、無駕照）、通緝（1.5%）、前科。
    - 車：車牌（`GET_VEHICLE_NUMBER_PLATE_TEXT`，去掉空白）、車主（駕駛本人 85%）、行照、保險、失竊（0.8%）。
  - 嫌犯的紀錄依身分設定（`SetSuspect`）：罪責 >0.8 有通緝（>0.92 持械搶劫，否則竊盜），>0.6 有前科（竊盜、持有管制藥物），可能被吊銷駕照。
  - 失竊車輛報案的車標為失竊，車主另有其人。
  - 照片：property 模組的車商目錄快取（`mods\property\data\shop_catalog.txt`，貼圖名 = 顯示名稱小寫）→ `https://gametextures/<字典>/<貼圖>.png`。沒有這個檔或車商不賣的車（警車等）顯示「沒有照片」。
  - 注意：`GET_FILENAME_FOR_AUDIO_CONVERSATION` 回傳的是遊戲重複使用的同一個緩衝區，連續呼叫兩次前一個會被覆蓋（車型和廠牌曾經都顯示成廠牌），每次都要先複製。
- 車上電腦（`mdt.cpp` + `web/mdt.lspd`，遊戲內瀏覽器）：
  - 在警車上按 F10（可改）或 F9 →「車上電腦」開啟。
  - 分頁：
    - 附近車輛：90 公尺內，照片、車牌、車型、距離、前車和嫌犯標記，點選即查詢。
    - 查詢：車牌或姓名；車牌辨識最後讀到的會自動填入。
    - 盤查紀錄：盤查過證件的人。
    - 案件與報告：進行中案件的經過和證物；報告草稿可勾選罪名、修改經過後提交。
  - 網頁函式：`mdt.state / nearby / vehicle / plate / person / people / reports / charges / submit`。
- 車牌辨識：
  - 在警車上每 0.3 秒找正前方 3–30 公尺、左右 3.5 公尺內最近的車。車牌顯示在小地圖旁，失竊時是紅字。
  - 每台車第一次讀到時，若失竊或車主有通緝，就發出警示音並通知。
- 向調度查詢（無線電）：
  - 從 F9 →「向調度查詢」（前車與最近 6 台車），或動作選單的「向調度查詢此人」「查車牌」發出。
  - 3.5–7 秒後回覆一行，例如「車牌 63DEX945，先知 XS，車主 …，已報失竊」或「Jose Garcia，生日 …，駕照有效，前科：竊盜、持有管制藥物」，同時記入案件。
- 搜查（`search.cpp`）：
  - 搜身約 3.5 秒（`CODE_HUMAN_POLICE_INVESTIGATE`）。
  - 搜車分五區：駕駛座、副駕駛座、置物箱、後座、後車廂（機車只有兩區）。每區先走到對應車門外、開門，翻找 4.5 秒（`PROP_HUMAN_BUM_BIN`），再關門。可以選單區、選「全部（剩下的）」依序搜，或交給支援。
  - 搜查中自己移動就會中斷。
  - 內容依嫌犯產生：
    - 武器在駕駛座或置物箱（60%）。
    - 第 N 級管制藥物在置物箱或後座。
    - 酒醉時副駕駛座有開封的酒瓶。
    - 失竊車後車廂有疑似贓物（50%）。
    - 其他是雜物（收據、行照、運動包、備胎等）。
  - 搜身會找到武器和管制藥物，並沒收。
  - 找到的證物會記入案件，並建議罪名。
- 支援協助：`units::Borrow` 借出最近、在車外、沒在忙的支援警員（他的單位不再指派他），搜完歸還，結果用「支援：…」通知。
- 動作選單（按住 E）新增：向調度查詢此人、查車牌、搜身／請支援搜身、搜車（分區子選單）。嫌犯不在車上時，在嫌犯的車旁按住 E 就是搜車選單。「押上警車」改為 60 公尺內的任何警車（支援停車時常常在 40 公尺外）。
- 報告：
  - 案件從受理開始記錄：受理、發現、嫌犯每個狀態（逃逸、逃跑、反抗、投降、靠邊、上銬、押上警車）、查詢結果、搜查結果。
  - 結案時產生草稿：日期時間、地點、結果、涉案人、證物、建議罪名（預設勾選）、經過。
  - 提交後評分：基本 60 分，有證據支持的罪名每項 +8、沒有支持的每項 −10、漏掉的建議罪名每項 −5，經過的長度最多 +20。存在遊戲存檔（`officer_reports`），之後用在升遷評價。
- 實測（失竊車輛報案，嫌犯設為會配合，三次）：
  - 開警燈後嫌犯靠邊停，叫他下車。
  - 搜身找到手槍和第二級管制藥物；分五區搜車，後車廂找到疑似贓物。自己搜和請支援搜都試過。
  - 調度回覆車牌（已報失竊）和人（前科）；車牌辨識跳出失竊和通緝警示。
  - 上銬、押上支援的警車後結案，車上電腦出現報告 #1。勾選罪名提交後得 64 分。
  - 支援拔槍包圍嫌犯有在畫面上確認。

### 53.13 載送與收押（2026-10-21）

- 使用者的設計：
  - 依罪名決定送哪裡。
  - 到場後押進門，用簡化的收押選單處理（有讀秒和動作）。
  - 可以交給支援代送。
  - 途中嫌犯會講話，有機會時會逃跑，開車方式計入報告分數。
- 案件改成「收押完成」才結束（`custody::Booked`），不再是押上警車就結束。
- 目的地（`custody.cpp`）：
  - 警局：Mission Row、La Mesa、Vespucci、Davis、Sandy Shores、Paleto Bay。
  - 監獄：Bolingbroke。
  - 輕罪預設送最近的警局。有重罪預設直送監獄：以武器攻擊警察、劫車、非法持有武器、第一級或第二級管制藥物、脫逃、通緝。
  - F9 →「載送」可以改目的地。重罪送警局也可以，收押後會註記移送監獄；輕罪不能送監獄，到門口會被拒收。
  - 各地點的停車點和門口，Mission Row、La Mesa、Sandy Shores 沿用 §53.4 確認過的位置。其他四處是傳送過去用俯視鏡頭和側面截圖找到的：
    - Vespucci：正門台階上。
    - Davis：Davis Ave 的側門走道。
    - Paleto Bay：正門。
    - Bolingbroke：「INMATE RECEIVING GATE 1」受刑人收容大門。
  - 故事模式沒有警局的地圖圖標（`GET_FIRST_BLIP_INFO_ID(60)` 只找到本模組自己加的）。
- 載送途中：
  - 押上車時關後車門。開始自己載送時，支援自動收隊。
  - 嫌犯對話：開車時每 25–50 秒用字幕說一句。依個性分成求情、敵意（同時播罵人的語音）、老手沉默、酒醉、管制藥物、喊冤。
  - 計分：
    - 扣分：
      - 車體健康一次掉超過 25 算碰撞，−3。
      - 超過 120 km/h 持續 3 秒算超速，−2（每 20 秒最多一次）。
      - 載送時開警笛超過 5 秒，−5（一次），並提醒「不是緊急勤務」。
      - 開車扣分最多 20 分。
    - 加分：沒被扣分、嫌犯也沒逃，+5。
  - 脫逃：
    - 機會：後車門開著或壞了、車子壞掉／起火／翻覆，或員警離車超過 35 公尺達 20 秒。押上車後前 8 秒不判定。
    - 判定：每 4 秒擲一次骰，膽量 = nerve×0.5 + guilt×0.3（車壞 +0.3、酒醉 −0.1；有人在旁邊 −0.4），擲出小於膽量×0.35 就逃。
    - 逃跑時銬著手：跑不快、不會反抗、不會劫車、不會換裝。被抓到就回到上銬狀態，可以再押上車。案件 −15，罪名加「脫逃」。
- 到場：
  - 警車停在停車點 25 公尺內、員警下車，嫌犯就下車跟著員警走。

### 53.14 支援上限、支援接手載送，以及自動測試找到的問題（2026-10-21）

- 支援上限依案件嚴重程度（使用者要求；`units::MaxUnits`）：
  - 一般勤務 1 組。
  - 有處理中的案件 2 組。
  - 追捕中、嫌犯持有武器或反抗 3 組。
  - 嫌犯開槍攻擊員警 4 組。
  - 呼叫支援時，調度會回報「目前狀況（…）最多派 N 組支援，已經有 M 組」。F9「呼叫支援」旁邊顯示目前組數和上限。
- 交給支援載送：
  - 以前支援的車要在旁邊才能選。現在 400 公尺內有支援就能選。
  - 選了之後，`units::Summon` 叫 600 公尺內最近的一組開車過來（在場、追捕中、趕來中的都算）。車開到嫌犯 20 公尺內就押上車。
  - 120 秒還沒到，就提示「支援的車過不來：押上你的警車」。
  - 要借支援警員時，挑 120 公尺內最近的一位。還在車上的距離多算 15 公尺，收隊中和載送中的不挑。
- 請支援搜身、請支援搜車：
  - 120 公尺內沒有支援警員時，選項反灰，標示「沒有支援」或「支援還沒到」。以前要按下去才說找不到人。
  - 支援警員還在車上時，先下車再走過去。
- 選單關閉時的按鍵漏給遊戲：
  - 關選單按的返回鍵或選擇鍵，在車上時遊戲也收到了，造成下車或上車。
  - 修法：關閉後 350 毫秒內繼續擋住這些控制。
- Mission Row 門口按住 E 沒開收押選單：
  - 原因：收押的門口和上下班的門口捷徑（§53.1，「按 E 去停車場」）在同一處，E 被捷徑拿走了。
  - 修法：收押中不觸發門口捷徑。
  - 門口加上「收押入口」圖標和 GPS 路線。
  - 員警或嫌犯沒到位時會提示「嫌犯還沒跟上來」或「再靠近門口一點」。嫌犯要在門口 10 公尺內（原本 7 公尺）。log 會記兩人離門口的距離，以及收押員在不在。
- 嫌犯決策（`suspect.cpp`）：
  - 很膽小的嫌犯也會逃跑，因為罪惡感直接加到逃跑分數。改成罪惡感要有膽量才會變成逃跑：flee = nerve×0.3 + guilt×0.8×(0.35 + 0.65×nerve) − 壓力×0.35。
  - 配合和拖延之間會一直來回跳。改成要連續兩次判定都一樣才切換。
  - 嫌犯死亡或消失時寫進 log（血量、兇手、死因），用來查偶爾出現的「剛上銬就消失」。
  - 支援警員舉槍掩護（cover）時，嫌犯原本只把它算成「附近一名警察」（壓力 +0.15）。員警走去搜車，嫌犯就從配合變成逃跑。
    - 改成 10 公尺內有掩護中的支援警員時，壓力 +0.3，逃跑分數 −0.25（`units::Covering`）。
    - 嫌犯看不到員警時，這份壓力仍然算數。
- 押上警車反灰時沒有原因：
  - 改成標示「警車在 N 公尺外」或「附近沒有警車」。
  - 要押上車的警車必須在 60 公尺內。上銬的嫌犯會跟著員警走。
- 失竊車輛：車牌辨識讀到這通案件的車，也算「找到那台車」（以前只看員警有沒有看到嫌犯）。
- 路人把員警拖下警車、把車開走（自動測試中出現過幾次）：
  - 用測試 hook 在員警被劫車的當下記錄劫車者（`IS_PED_BEING_JACKED`、`GET_PEDS_JACKER`）。結果是一般男性路人：關係群組 CIVMALE，不是任務實體，也不是嫌犯。
  - 本模組只在有槍聲時才叫路人逃跑，這次沒有開槍，所以是遊戲本身的路人行為。警車在路上停很久時發生，例如測試機器人卡住的時候。
  - 修法：值勤中的員警不會被拖下車（`SET_PED_CAN_BE_DRAGGED_OUT`）。下班後恢復。
- 支援到場後，員警一開車離開，支援就留在原地（自動測試中出現）：
  - 原因：支援是在員警還在開車時「到場」的（車在 25 公尺內就算到），下車加入員警的小隊。小隊成員只會用走的跟，所以留在原地。
  - 結果：「請支援搜車」一直顯示「支援還沒到」。交給支援載送時，支援的車還停在 571 公尺外，開過來前測試就逾時了。
  - 修法（`units.cpp`）：
    - 員警上車時，支援先離開小隊，不跟著擠進員警的車。
    - 員警的車開動後，支援回到自己的車跟上。警燈和開法跟員警一樣：員警開警燈就緊急行駛，沒開就一般行駛。
    - 員警下車、支援的車在 25 公尺內時，支援才算到場，下車重新加入小隊。
    - 追捕中，支援的車離嫌犯還遠時先開過去，到了才下車。掩護、徒步追、交火都是這樣。以前同車的另一名警員會在半路就下車。
- 上銬的嫌犯跟著員警走時，員警走快或用跑的，嫌犯就落在後面。改成落後超過 6 公尺時，嫌犯改用小跑跟上。
- 支援警員正在搜車時把嫌犯交給支援載送（自動測試中出現）：
  - 那位警員被小組叫回車上，搜查工作卻還在，兩邊搶著指揮他。支援的車已經開走載送，搜車結果還陸續回報。
  - 修法：小組要收回借出的警員時（載送、開車過來、收隊），他的搜查停在當下（`search::Drop`），並通知「支援：搜車先停在這裡，剩下的區域還沒搜」。剩下的區域員警可以自己搜。
- 嫌犯「已靠邊停車」，車卻又開走（自動測試中出現）：
  - 嫌犯決定靠邊時，會拿到「開到前方 30 公尺路邊」的開車任務。車速低於 1 m/s 持續 2.5 秒就算停好，但只踩 1 秒煞車，開車任務沒取消。
  - 車還沒開到那個點就停下（例如被支援的車或前車擋住），煞車一結束就繼續開，可能繞路開到很遠。狀態仍是「已停車」，員警走過去時車已經在 70 公尺外。
  - 修法：判定停好時一併清掉開車任務，嫌犯坐在車上等。之後想跑還是會由決策重新下任務。

### 53.15 失竊車輛：竊嫌把車開到別處停放，找不到就失去蹤跡（2026-10-22）

- 問題（§54.1 自動測試中出現）：竊嫌用 `TASK_VEHICLE_DRIVE_WANDER` 在整張地圖上一直亂開。員警可能一直找不到，案件也不會自己結束。
- 使用者選擇兩種做法都做：
  - 竊嫌把車開到幾公里外停在路邊，人在附近等。
  - 一直找不到就由調度結束案件。
- 停放地點（`dispatch.cpp` 的 `PlanDropOff`）：
  - 報案時，在離報案地點 2–4 公里處隨機挑一點。
  - 遠處的路網節點平常沒有載入。每個 tick 對那一帶（±200 公尺）呼叫 `REQUEST_PATH_NODES_IN_AREA_THIS_FRAME`。等 `ARE_NODES_LOADED_FOR_AREA` 回 true 後，用 `GET_NTH_CLOSEST_VEHICLE_NODE_WITH_HEADING` 找最近的路。
  - 那條路要符合三個條件：
    - 離挑的點 300 公尺內；
    - 離報案地點 1.5 公里以上；
    - 最多 2 線道，不停在大馬路上。試過 5 次以上就不限線道。
  - 3 秒內沒載入、或那一帶沒有路（海上、山裡），就換一點。8 次都不行就照舊亂開。
  - 實測距離 2151–3996 公尺。
- 竊嫌（`suspect.cpp`）：
  - 開過去：`suspect::HeadFor` 讓還沒察覺警察、正在開車的竊嫌用 `TASK_VEHICLE_DRIVE_TO_COORD_LONGRANGE` 開過去。車速 1 m/s 以下超過 30 秒，就重新下任務。
  - 停車：到了 35 公尺內，切到新狀態 park，靠到路邊停好。然後熄火下車，車留在原地。
  - 等待：在附近等 4–8 分鐘。
    - 先走到離車 20–50 公尺的地方（`GET_SAFE_COORD_FOR_PED`），在那裡抽菸或滑手機。
    - 遠離玩家的地方沒有載入 navmesh，找不到落腳點。這時先站在車旁，之後每次思考再找一次。員警接近時 navmesh 會載入。
  - 時間到了、員警也不在視線內，竊嫌就走掉（blend，log 寫「nobody came」）。
  - 等待中發現員警，或停車途中後面有警燈，都和以前一樣進入決策（拖延、配合、逃跑等）。
- 調度：
  - 目擊回報：車停在路邊、駕駛座沒人時，改成「有民眾看到那台…停在…路邊」。
  - 找到停著的車時，依竊嫌的位置通知：
    - 竊嫌離車 8 公尺以上：「找到那台…了：停在路邊，車上沒人。有民眾看到駕駛下車往…邊走，可能還在附近。」
    - 竊嫌在車旁：「找到那台…了：停在路邊，駕駛就在旁邊。」
    - 報告記一筆「車輛停放路邊，駕駛已離開車輛」。
  - 新增的結案方式：
    - 找到車時竊嫌已經走掉：「失竊車輛已尋獲，竊嫌已經離開」，報告結果寫「尋獲失竊車輛，竊嫌不明」。
    - 找到車之後竊嫌才逃掉：「嫌犯逃脫，失竊車輛已尋獲」。
    - 接案 15 分鐘還沒找到車：「一直沒有找到那台…，失去蹤跡，轉為協尋」。竊嫌交還給遊戲。
  - 案件結束或收隊時，那台車也交還給遊戲（`SET_VEHICLE_AS_NO_LONGER_NEEDED`），不會一直留在地圖上。
- 自動測試（§54.1 的機器人）：
  - 新增隨機選項「晚 5 分鐘才出發」，用來測試找停著的車。
  - 竊嫌在車外、還沒察覺時，機器人下車走過去。
  - 找車階段的時限改成 960 秒，配合 15 分鐘失去蹤跡。
  - 調度結束案件（失去蹤跡、尋獲車輛）記成一種結果，不算失敗。
  - 支援說「支援的車過不來：押上你的警車」時，機器人改押上自己的警車（以前會一直等到逾時）。
- 結果（第 25–27 批，共 9 次，每次都找到停放地點，距離 2056–3996 公尺）：
  - 7 次竊嫌開到地點停車：
    - 5 次在停著的車旁邊逮捕竊嫌；
    - 1 次機器人晚到，竊嫌已經走掉，以「失竊車輛已尋獲，竊嫌已經離開」結案；
    - 1 次 15 分鐘沒找到，以「失去蹤跡」結案。這次機器人有 11 分鐘沒下任何指令，原因不明，已加上找車階段的軌跡紀錄。
  - 2 次還在路上就被攔下：1 次逮捕，1 次一般難度的竊嫌開車逃脫。
  - 等待的地方：修正前竊嫌都站在車旁（navmesh 沒載入）。修正後 3 次中有 2 次已經走開，調度說「有民眾看到駕駛下車往西邊走」。
  - 機器人本身沒完成的：
    - 1 次支援的車在不同高度的路上過不來，機器人不懂那則提示（已修）；
    - 1 次載送到 Bolingbroke 時卡在高速公路車陣裡。

## 54. 背景測試：不搶焦點、不佔螢幕（2026-10-21）

- 使用者要求：測試時可以同時用電腦。以前的測試靠 SendInput 和整個螢幕截圖，遊戲必須在最前面。
- 只在 `loader.json` 的 `debugRemote` 為 true 時才有作用（`src/loader/debug/remote.cpp`）：
  - Named pipe `\.\pipe\gtave-modloader`，可同時多個連線。每行一個指令，回一行 `ok …` 或 `err …`。
  - 按鍵：`key F9` 會把自訂訊息 post 到遊戲視窗，由 overlay 的 WndProc 交給 `mods::OnKeyDown`，只觸發 mod 快速鍵，遊戲收不到。
  - 遊戲控制：`control <id> [ms] [值]`，每個 script tick 呼叫 `SET_CONTROL_VALUE_NEXT_FRAME(0, id, 值)`，直到時間到。
    - 實測有效的：角色輪盤（19）加選第四個角色（169），按住 E（51），選單的上下、選擇、返回（172–177）。
    - 本模組選單用的 `IS_DISABLED_CONTROL_JUST_PRESSED` 也讀得到。
  - 截圖：`shot <路徑>`。在 overlay 的 Present 回呼裡，把當下的 back buffer 複製到 readback 緩衝區，轉成 BGRA，再用 WIC 存成 PNG。
    - 畫面包含 overlay。
    - 支援 R8G8B8A8、B8G8R8A8、R10G10B10A2、R16G16B16A16_FLOAT（scRGB 轉 sRGB）。
    - WIC 的 PNG 編碼器不接受 32bppBGR，要用 32bppBGRA。
  - 視窗：
    - 遊戲視窗一出現就移到所有螢幕右邊（不最小化，最小化會停止 Present），並把焦點交還給 z-order 中下一個可見的一般視窗。遊戲套用顯示設定時會把視窗拉回來，所以每 0.25 秒檢查一次，再移出去。`window restore` 可以叫回來。
    - 靜音用遊戲自己的音訊工作階段（`ISimpleAudioVolume`），可用 `mute on|off` 切換。
  - `story`：從主畫面繼續故事模式，等於 UI 上那一下點擊。
  - 通知：`ml::Notify` 也會寫進 mod 的 log（`notify: …`），測試看得到玩家收到的訊息。
- 用戶端 `tools/gtactl.py`：
  - `launch`：
    - 暫時把 GTA 的 `settings.xml` 改成視窗模式（Windowed=1），關掉 PauseOnFocusLoss，開 `debugRemote`。
    - 用 Steam 啟動，等 pipe 出現，在主畫面送 `story`。
  - `quit`：關閉遊戲，把設定改回原本的值（`settings.xml` 先備份成 `.gtactl-backup`）。
  - 測試步驟：`key:F9`、`ctl:173,90`、`hold:51,800`、`shot:a.png`、`log:<regex>,<秒>`、`raw:<指令>`。
- 實測：
  - 遊戲在螢幕外跑完整個流程，從啟動、切換成警察、接案、追車、收押到結案。
  - 使用者的 Chrome 全程留在前景。
  - 截圖是 1920×1080 的遊戲畫面。
- 啟動失敗的情況（2026-10-22）：
  - Rockstar Launcher 回報服務錯誤（`Reporting error (id=10, result=400)`）後，取消這次啟動（`GLA CE: Task canceled prior to creation`）。遊戲沒有啟動，Launcher 卻留著。
  - Steam 把 Launcher 當成遊戲還在執行，之後的啟動都停在 `WaitingPrevProcess` 就結束，pipe 一直不出現。
  - 處理方式：關掉這次啟動留下的 Launcher、SocialClubHelper、PlayGTAV，等 Steam 的 `content_log.txt` 不再顯示 App Running，再啟動一次。

### 54.1 自動測試機器人（2026-10-21）

- 緣由：
  - 先試過讓語言模型當測試玩家。
  - 使用者認為直接寫啟發式決策比較好也比較快，要換花樣只要加一個隨機選擇器。
- 機器人與橋接都沒有放進 repo，屬於暫時的測試工具：
  - 機器人是 Node 腳本 `police-bot.mjs`。
  - 橋接是 mod 裡的 `zz_jev.cpp`。
- 橋接：
  - 每 0.5 秒寫出狀態檔，內容有玩家位置、車速、是否在警車上、警燈段數、是否在搜查中、離自己警車多遠。另外有嫌犯的行為、是否在車上、是否上銬、距離、車速，還有選單、載送、GPS 目的地。
  - 讀指令檔來執行：開車（一般、繞過前車、緊急）、追車、停車、上下車、走或跑向嫌犯、走向警車、把卡住的車放回路上、舉槍。
- 流程分成幾個階段，各有時限：準備 → 叫支援 → 接案 → 找車 → 攔停 → 上前 → 處理 → 押上車 → 改目的地 → 開車載送 → 收押 → 結案。
- 隨機選擇器：用種子決定每次的選擇，同一個種子可以重跑。選擇項目有：
  - 嫌犯難易度、是否叫支援、盤查證件、向調度查詢；
  - 搜身（自己、支援、不搜）、搜車（一區、全部、支援、不搜）；
  - 載送（自己、支援）、目的地、開車方式（守規、警笛、魯莽）、途中是否丟下嫌犯、收押選單（全部或逐步）。
  - 另外有 8% 的機率插入干擾動作，例如舉槍或開車上電腦。
- 判斷依據：
  - mod 的 log（`notify:`、`custody:`、`dispatch:` 等）和狀態檔。
  - 選單用文字標籤選擇，並核對游標位置。
  - 每個階段只認自己開始之後的 log，避免上一輪的結案訊息造成誤判。
  - 階段逾時後，它留下的迴圈會自己停止（Node `AsyncLocalStorage` 帶著各階段自己的取消旗標）。
- 報告：每批一份 Markdown 和 JSON。內容有每個階段的耗時、失敗時的截圖、發現（error、timeout、note）、結案評分的加扣分。攔停失敗時另附每 15 秒的追車軌跡。
- 找到並已修好的 mod 問題，見 §53.14：
  - 選單關閉時按鍵漏給遊戲；
  - Mission Row 收押門口的 E 被上下班捷徑拿走；
  - 押上警車反灰時沒有原因；
  - 支援掩護時嫌犯照樣逃跑；
  - 車牌辨識讀到案件車輛時不算找到；
  - 路人把員警拖下警車；
  - 支援不會跟著員警的車走；
  - 支援搜車中被叫去載送，搜查卻沒停；
  - 嫌犯靠邊停車後車又開走。
- 機器人本身的問題：
  - 停在前車後面不動：改用繞行開法。
  - 走向嫌犯時對方開車跑了：偵測後回到追車。
  - 找車時總是落後：依目擊位置的變化推算前進方向。
  - 搜車還沒結束就按 E：等搜查結束。
  - 每 3 秒重下一次開車或追車指令，AI 一直重新起步：改成沒有進展才重下。
  - 車卡在路邊或高台：30 到 45 秒沒進展就放回最近的主要道路。
  - 嫌犯已經逃脫、案件結束了，追車迴圈還在跑：處理嫌犯的各階段看到 `dispatch: call over` 就結束。
  - 嫌犯退到 3 公尺外時，員警站在嫌犯車門邊按 E，會打開「搜車」，不是「處理嫌犯」（mod 的設計：3 公尺內先處理嫌犯，否則搜車）。改成關掉那個選單、走近一點再按。
  - 押上車的時限 90 秒不夠：警車在 100 公尺外要帶嫌犯走過去，或支援要先把車開過來。改成 240 秒。
  - 徒步追逐結束時離警車 350 公尺，帶嫌犯走回去來不及。改成警車超過 100 公尺時，用警用選單「叫巡邏車開過來」，跟玩家會做的一樣。
  - 測試失敗時，機器人用「收隊」清場，案件會以「嫌犯逃脫」結束。所以報告裡失敗那幾次的「嫌犯逃脫」是清場造成的，不是 mod 判定的。
  - 嫌犯站在自己車門邊，支援警員也在旁邊時，機器人走過去可能停在約 3 公尺處（被擋住），按 E 會在「處理嫌犯」和「搜車」之間跳。機器人會關掉選單再靠近，通常 1 到 3 次就成功。玩家自己走近就沒這個問題，所以 mod 不改。
- 結果（每批完整結案次數）：
  - 第一批 5/8；修正後下一批 6/8，其中 1 次由支援載送。
  - 第 18、19 批 4/8：沒結案的是 1 次找不到車、2 次押不上車、1 次按 E 沒開到處理嫌犯。
  - 指定支援流程的第 20 批 0/3：1 次找不到車，2 次交給支援載送逾時（支援沒跟上，以及搜車與載送衝突，見 §53.14）。
  - 第 21 批 2/3：沒結案的 1 次是嫌犯靠邊後車又開走（見 §53.14）。
  - 第 22 批 1/4：2 次嫌犯轉為暴力（機器人不開槍，屬預期結果），1 次警車在 349 公尺外押不上車（機器人已改用「叫巡邏車開過來」）。
  - 全部修正後的最後兩批 7/7：隨機 4 次，加上固定叫支援 3 次（其中 2 次交給支援載送）。
    - 支援搜車到一半時員警把嫌犯押上自己的車，搜查會停下並通知（`search: backup called away, 3 left`）。
- 失竊車輛的竊嫌會在整張地圖上一直亂開（`TASK_VEHICLE_DRIVE_WANDER`），員警可能一直找不到，案件也不會自己結束。已改成竊嫌把車開到別處停放，15 分鐘找不到就失去蹤跡，見 §53.15。
